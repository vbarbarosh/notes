# Notes app — security & code audit

- **Date:** 2026-09-02
- **Scope:** `@vbarbarosh/notes` — Express file-system-backed note app (`src/`), job runner, terminal, chunked uploads, static SPA, Docker/authwall deployment.
- **Commit:** `85e5d0e` (main)
- **Method:** full read of server routes and helpers, trusted `@vbarbarosh/*` library sources, front-end render path, job scripts, Docker/compose. Test suite run (60 passing) and `npm audit` in a `git archive` copy under scratchpad. No changes made to `/app`.

This is the first audit in this register. Findings use the S-series and carry forward from here.

## Trust model (read this first)

The app has **no authentication of its own**. It reads the current user from the `X-Auth-User` request header and expects to sit behind the [authwall](https://github.com/vbarbarosh/authwall) reverse proxy, which authenticates the user and injects that header. When the header is absent, the request falls back to a shared anonymous workspace rooted at `data/` (`src/index.js:39-41`).

Almost every finding below is an instance of one theme: **the app trusts its own network boundary completely.** If authwall is bypassed, misconfigured, or simply not in front of the app, the app offers an interactive shell and full impersonation to anyone who can reach its port. The `Dockerfile` sets `LISTEN=0.0.0.0`, so the container binds all interfaces; only `docker-compose.yaml` keeps it private by publishing authwall alone.

## S1 — Critical — Stored XSS to arbitrary JavaScript via note rendering

**Where:** `src/static/js/components/vendor/markdown.js`, consumed by `note-card.js:150`.

The markdown component builds its renderer with raw-HTML passthrough enabled:

```js
const md = markdownit({ html: true, linkify: true, highlight: highlight_markdown_code });
```

and then, critically, compiles the rendered HTML **as a Vue template** rather than inserting it as inert markup:

```js
this.spec = Vue.markRaw({template: this.html || '<span></span>', data: () => this.data ?? {}});
```

There is no sanitizer (no DOMPurify, no allowlist) anywhere in the path. Two separate code-execution routes result:

1. **Raw HTML with event handlers.** `html: true` passes note text such as `<img src=x onerror=alert(document.cookie)>` through verbatim; once compiled and mounted, the browser fires the handler.
2. **Vue template injection.** Because the string is a template, Vue expressions execute. A note body can reach the component instance and the global scope through the render context.

A note is authored by writing its `README.md`, and notes are viewable through the SPA and shared by the `/r/<uid>` backlink URLs added in the latest commit. Any content that one user can get another to open runs script in the victim's session on the app origin — which, given S2, is a origin that also exposes a shell.

**Fix:** render markdown to sanitized, inert HTML. Turn off `html` (or run the output through DOMPurify with a strict allowlist) and stop compiling user content as a Vue template — bind it with `v-html` on a sanitized string, or better, render to a static vnode tree. Add a Content-Security-Policy (S7) as defense in depth.

## S2 — Critical — Interactive shell (RCE) through the jobs API

**Where:** `src/routes/jobs.js` — `jobs_create_terminal`, `spawn_terminal_session`, `attach_ws`.

`POST /api/v1/jobs/terminal` spawns a real interactive PTY:

```js
const pty = node_pty.spawn(process.env.SHELL || 'bash', [], { cwd: note_root, env: {...process.env, TERM: 'xterm-256color'} });
```

kept alive in-process and wired to a WebSocket at `/api/v1/jobs/:uid/tty` that pipes keystrokes straight to the shell. This is an intended feature, but its only access control is the trust boundary. Consequences:

- Any principal the app accepts gets **arbitrary command execution** inside the container, with the server process's privileges and its full environment (`{...process.env}` — every secret the process holds is exported into the shell).
- When no `X-Auth-User` header is present, the request runs in the shared anonymous workspace (`req.user_dir = data_dir`) and the terminal still spawns. So an app reachable **without** authwall in front of it hands an **unauthenticated** shell to any network client.
- The non-terminal job path (`spawn_job_process`) runs bundled scripts under `src/jobs/*/bin/run`; these are repo-controlled today, but the same spawn machinery would execute any script dropped into that directory.

**Fix:** treat the terminal as a privileged capability, not a default one. Gate it behind an explicit server-side allowlist of users/roles rather than mere presence of a header; disable it entirely when unauthenticated (no `X-Auth-User`); scrub the child environment to only what the shell needs; and document that the app must never be exposed without authwall.

## S3 — High — `X-Auth-User` is trusted with no shared secret

**Where:** `src/index.js:38-52`.

The user identity is taken directly from the client-supplied header:

```js
req.user_uid = req.headers['x-auth-user'] ?? null;
```

The only validation is a character-class check (`[^0-9a-zA-Z_-]`) to keep the value path-safe. There is no shared secret, signature, or mutual-TLS check proving the header actually came from authwall. Anyone who can reach the app port directly can:

- set `X-Auth-User: <any existing user>` and **read, modify, and delete that user's notes and files**, or
- omit it and operate in the shared anonymous space.

authwall does not strip an incoming `X-Auth-User` guarantee that is visible in this codebase, so header-smuggling through the proxy is worth testing on the authwall side too.

**Fix:** authenticate the proxy→app hop. Share a secret header/token that the app verifies (rejecting requests without it), bind the app to localhost / a private network only, and have authwall explicitly overwrite (not merely add) `X-Auth-User`.

## S4 — High — Terminal WebSocket authorized by knowledge, not identity

**Where:** `src/routes/jobs.js` — `attach_ws`, `resolve_ws_user`; client at `src/static/js/components/terminal-panel.js:109-113`.

Because browsers cannot set headers on a WebSocket, the upgrade handler reads the user from the URL query string:

```js
user = new URL(req.url, 'http://localhost').searchParams.get('user');   // resolve_ws_user
```

and then looks up the live session by `session_key(user_uid, uid)`. Neither value is a secret: `user_uid` is the plain username, and `uid` is a timestamp-derived job id (`YYYYMMDD_HHMMSS-terminal…`, `is_safe_job_uid`). The handler never confirms that the connecting party is authenticated as that user — it simply believes the query parameter. Any client that can reach the port and knows (or guesses) a victim's username and an active terminal job id can **attach to that live shell**, seeing its output and sending input. With no proxy in front, this needs no credentials at all.

**Fix:** mint an unguessable per-session token when the terminal is created, return it only to its creator, and require it on the WS upgrade. Authorize the upgrade against the proxy-authenticated identity (see S3) rather than a client-provided query value.

## S5 — High — User files served inline, same-origin, with attacker-controlled type

**Where:** `src/index.js` `data_fetch` (`/r/*`), `src/routes/notes.js` `notes_file_fetch` (`/api/v1/notes/:uid/files/*`).

Uploaded files are returned with `res.sendFile(full)`, which sets `Content-Type` from the file extension and serves inline. There is no `X-Content-Type-Options: nosniff`, no `Content-Disposition: attachment`, and no CSP. A user can upload an `.html` or `.svg` file and get it served as active content from the **app's own origin**, yielding stored XSS on anyone who opens the link. The `overwrite=1` path (`fs_write_over_file`) further allows writing arbitrary files under a note's `files/apps/` subtree, which the SPA surfaces as runnable "apps."

In the per-user model this is largely self-XSS, but the `/r/<uid>` share URLs and any note-sharing move it cross-user, and it compounds S1/S2.

**Fix:** serve user content with `Content-Disposition: attachment` (or from a separate, cookieless origin/sandbox domain), always send `X-Content-Type-Options: nosniff`, force a safe `Content-Type` for non-media (e.g. `text/plain` or `application/octet-stream`), and never serve SVG/HTML inline on the app origin.

## S6 — High — Vulnerable dependencies

`npm audit --omit=dev` in a clean copy reports 9 advisories (6 high). The reachable ones:

- **sharp < 0.35.0** (installed 0.34.5) — inherited libvips image CVEs. Directly reachable: `sharp(source_file)` runs on every uploaded image for thumbnails and metadata (`src/index.js:213`, `file_meta_cache.js`). A malicious image is processed automatically.
- **ws 8.20.1** — memory-exhaustion DoS from tiny fragments; the terminal transport is `ws`.
- **multer 2.1.1** — two DoS advisories; multer handles every upload.
- **path-to-regexp**, **qs** — ReDoS / DoS in the Express stack.

**Fix:** `npm audit fix` for ws/multer/path-to-regexp/qs; `npm audit fix --force` (or a deliberate bump) for `sharp@^0.35`. Re-run the suite; sharp's major bump is the only breaking one.

---

## S7 — Medium — No security headers

**Where:** `src/index.js` (no `helmet`, no header middleware).

Responses carry no `Content-Security-Policy`, `X-Content-Type-Options`, `X-Frame-Options`/`frame-ancestors`, `Referrer-Policy`, or `Strict-Transport-Security`. This removes the main mitigations that would blunt S1 and S5, and leaves the SPA open to clickjacking and MIME sniffing.

**Fix:** add `helmet` (or an explicit header middleware) with a strict CSP — no inline script, no `unsafe-eval` — after moving the SPA's CDN `<script>` tags (unpkg/jsdelivr) into that policy or self-hosting them.

---

## S8 — Medium — Session cookies and identity logged in plaintext

**Where:** `@vbarbarosh/express-helpers/src/express_log.js`, enabled in `src/index.js:29-31`.

Every request logs the full header set, including `cookie` (the authwall `connect.sid` session token) and `x-auth-user`, to daily plaintext files under `data/logs`. Confirmed in the checked-in dev logs (`data-notes/logs/http-2026-06-28.log` contains live `connect.sid` values). Anyone who reads a log file obtains session tokens usable to impersonate users at authwall until they expire.

**Fix:** redact `cookie`, `authorization`, and `x-auth-user` before logging; restrict log-file permissions and retention.

---

## S9 — Medium — No rate limiting or job/terminal quotas

**Where:** `src/routes/jobs.js`, `src/routes/files.js`, `src/routes/notes.js`.

Nothing bounds how many jobs, terminals, or chunked uploads a caller can create. Each terminal spawns a persistent bash PTY held in process memory; `youtube-mp3` spawns `yt-dlp`; chunked uploads accept 25 MB/chunk with an unbounded chunk count assembled to disk. A single caller can exhaust CPU, memory, PIDs, or disk.

**Fix:** add per-user concurrency caps (especially one/few live terminals), a global job ceiling, request rate limiting, and a total-size limit on assembled chunked uploads.

---

## S10 — Low — SSRF via redirect following in youtube-thumbnails

**Where:** `src/jobs/youtube-thumbnails/bin/run` — `download()`.

The initial URL is fixed to `https://img.youtube.com/vi/<id>/hqdefault.jpg`, but the function follows `Location` redirects to any host with no re-validation. The redirect target is YouTube-controlled rather than directly attacker-controlled, so impact is limited, but there is no allowlist, cap on redirect depth, or block on internal addresses.

**Fix:** cap redirect depth and re-validate each hop against an allowlist of expected YouTube hosts; refuse redirects to private/link-local addresses.

---

## S11 — Low — Prefix note resolution

**Where:** `src/routes/notes.js` and `src/routes/jobs.js` — `resolve_note_root_name`: `names.find(name => name.startsWith(note_uid))`.

A request with a short `note_uid` resolves to the **first** note directory whose name starts with it. This is by design for the `<uid>` vs `<uid>-<name>` scheme, but a truncated or shared prefix can silently resolve to a different note than intended and aids enumeration. Scoped to a single user's own notes, so impact is low.

**Fix:** require an exact `uid` match (the part before the first `-`) rather than a `startsWith` prefix.

---

## S12 — Low — Inconsistent path hardening

**Where:** `src/helpers/fs_path_safe_resolve.js` vs `src/helpers/fs_path_strict_resolve.js`.

File operations under `notes/:uid/files/*` use the strict resolver (rejects `.`, `..`, backslashes, absolute paths, NUL — well tested). But `/r/*` fetches and upload placement use `fs_path_safe_resolve`, which only strips leading dots per path segment and does not reject backslashes or resolve symlinks. It contains traversal in practice, but the two resolvers diverging invites a future gap.

**Fix:** standardize on the strict resolver for all request-driven path building, or document precisely why `/r/*` needs the lenient one.

---

## S13 — Info — Local dev secrets and logs in the working tree

`data-authwall/secret.key` (mode 0600), `data-authwall/db.sqlite3`, and log files containing session cookies exist in the working tree. They are **not** tracked by git and are excluded by both `.gitignore` (`/data-authwall/`, `/data`, `/data-notes/`) and the deny-by-default `.dockerignore`, so they neither ship in the image nor land in the repo — verified. Noted only so it stays that way; keep these paths out of any archive shared outside the container.

## What is done well

- **Path traversal on the file API** is handled carefully: `fs_path_strict_resolve` is strict and well tested; the `user_uid` character check prevents escaping the per-user root.
- **`.dockerignore` is deny-by-default**, so build context leaks are avoided.
- The **overwrite path is constrained** to `apps/` (`fs_write_over_file`).
- **Uploads are size-limited** per file (50 MB / 25 MB) and land in a temp dir before atomic rename.
- **Cache validation** in `file_meta_cache` checks size, mtime, version, and sha256 shape before trusting a cached entry.
- Test suite is green (60 passing).

## Recommended order of work

1. **S1** and **S5** — sanitize rendered markdown and neutralize inline file serving (stored XSS is the most directly exploitable issue).
2. **S3/S4/S2** — pin the trust boundary: authenticate the proxy hop, gate the terminal, token-protect the terminal WebSocket.
3. **S6** — bump vulnerable dependencies (sharp is reachable through image uploads).
4. **S7/S8/S9** — add security headers, redact logs, add quotas.
5. **S10/S11/S12** — hardening cleanups.
